# Codex Decision Router: полное описание для Claude Code

Документ описывает существующий инструмент и учитывает проверку состояния от 8 ноября 2026 года. Это контекст для изучения и возможной адаптации. Готовая интеграция с Claude Code пока не реализована и не проверена.

## 1. Назначение и замысел

Codex Decision Router — локальный плагин, который помогает основному агенту выбирать модели и уровни рассуждения для субагентов. Его цель — уменьшать расход лимитов подписки на рабочие задачи за счёт подходящего распределения сложности, контекста и ролей.

Пользователь пишет обычное подробное задание. В нём могут одновременно быть исследование, чтение кода, архитектура, реализация и проверка. Основной агент выделяет подзадачи. Небольшая внешняя модель принятия решений оценивает, какой из доступных профилей исполнителя подходит каждой подзадаче.

Настроенная цепочка:

- Основная модель принятия решений: `nace-ai/drex-max`.
- Резервная модель принятия решений: `typesafe/jev-1.14`.
- Поставщик API для обеих моделей: OpenRouter.
- Исполнители: штатные субагенты Codex под текущим способом авторизации и тарификации Codex.

OpenRouter оплачивает только решения маршрутизатора. Код, исследование и другие рабочие задачи выполняют субагенты Codex. Расход подписки, возможных дополнительных кредитов или API самого Codex определяется текущим режимом аккаунта.

«Наиболее эффективное распределение» здесь означает выбор по переданным описаниям возможностей и относительной стоимости. Математическая оптимальность, процент экономии и сохранение качества на любых задачах не доказаны.

- Идентификатор пакета: `jev-codex-router`.
- Версия: `0.2.1`.
- Установленный плагин: `jev-codex-router@habib-local`.
- Локальный marketplace: `habib-local`.
- Исходники: `<router-dir>`.
- Установленная копия: `~/.codex/plugins/cache/habib-local/jev-codex-router/0.2.1`.
- Каталог marketplace: `<marketplace-root>/.agents/plugins/marketplace.json`.

При проверке 8 ноября Codex сообщает `installed=true`, `enabled=true`, version `0.2.1`. Доступный MCP-инструмент `router_status` отвечает и распознаёт настроенный ключ OpenRouter. Значение ключа не запрашивалось и не выводилось. В этой проверке платных вызовов моделей не было; работоспособность ключа в живом запросе и доступ аккаунта к моделям этим не установлены.

Редактировать следует исходники. Кэш установки обновляется штатным механизмом Codex и не является местом разработки.

## 3. Из чего состоит инструмент

У инструмента три отдельных участника.

**Основной агент хоста:** понимает запрос, читает нужные инструкции проекта, составляет подзадачи и критерии готовности, определяет доступные модели, вызывает маршрутизатор, запускает исполнителей и проверяет результат.

**Python MCP-сервер:** проверяет данные, формирует запрос принятия решений, обращается к OpenRouter, обрабатывает резерв, проверяет вероятности, возвращает назначения и порядок запуска.

**Модель принятия решений:** выбирает один из профилей, перечисленных основным агентом для конкретной задачи. Возвращает структурированное решение с вероятностями.

Основной поток:

```text
Запрос пользователя
  → основной агент составляет задачи и допустимые профили
  → MCP route_tasks
  → Drex Max через OpenRouter
  → при необходимости Jev 1.14 для спорных вопросов
  → проверенный план назначений и зависимостей
  → основной агент запускает штатных субагентов Codex
  → проверяет результаты и собирает итог
```

Python-сервер сам не запускает субагентов. В его ответе `executed` всегда `false`. Применение плана реализуется инструкциями навыка и инструментами основного агента. Это существенная граница реализации.

## 4. Пользовательский запуск

В Codex достаточно отправить:

```text
$jev-codex-router:route-subagents
```

Дополнительная фраза «используй плагин для распределения моделей» не требуется. Полная инструкция уже находится в `skills/route-subagents/SKILL.md`.

При явном вызове навык предписывает основному агенту:

1. Взять последнюю незавершённую задачу из текущей переписки вместе с принятыми уточнениями.
2. Применить к ней маршрутизацию и продолжить разрешённую работу.
3. Сохранять этот выбор для задачи и её продолжений до завершения или изменения пользователем.
4. Если активной задачи ещё нет — кратко сообщить о готовности и применить маршрутизацию к следующему заданию в этом чате.

Этот сценарий задан инструкциями навыка. Плагин не перехватывает все сообщения и не устанавливает глобальный режим для других чатов. Явное упоминание в Codex и способ вызова навыков в Claude Code нужно рассматривать отдельно.

## 5. Модели и профили исполнителей

Профиль состоит из:

| Поле | Смысл |
|---|---|
| `id` | Локальный идентификатор профиля |
| `model` | Точное имя модели исполнителя, которое понимает хост |
| `reasoning_effort` | Уровень рассуждения исполнителя |
| `description` | Возможности и типы задач профиля |
| `cost_rank` | Условный относительный порядок стоимости: меньше — дешевле |

Несколько профилей могут описывать одну модель с разными уровнями рассуждения. `cost_rank` не является ценой токена, коэффициентом расхода подписки или измерением качества.

Основной агент получает доступные модели и параметры из текущего хоста. Маршрутизатор не обнаруживает их сам и не знает автоматически, какая новая модель сильнее на конкретной задаче.

Для каждой задачи основной агент передаёт `allowed_profiles` — допустимые достаточно сильные варианты — и `fallback_profile` — заранее выбранный допустимый профиль на случай неудачи обеих решающих моделей. Это отдельное понятие от резервной модели Jev.

## 6. MCP-инструменты

| Инструмент | Назначение | Обращение к OpenRouter |
|---|---|---|
| `router_status` | Версия, основные настройки, наличие ключа, путь к нему, счётчик вызовов | Нет |
| `preview_routing` | Проверка входа, формируемый запрос, размер и план зависимостей | Нет |
| `route_tasks` | Выбор профилей через Drex/Jev и возврат плана | Да, если есть выбор и доступен ключ |

В обычной работе достаточно проверить статус и вызвать `route_tasks`. Отдельный preview нужен при диагностике; обязательный preview на каждый запрос создавал бы лишнее повторение контекста.

Сервер работает по MCP stdio: JSON-RPC-сообщения построчно через stdin/stdout. Поддержаны initialize, ping, tools/list, tools/call. Результат инструмента возвращается в `content` и `structuredContent`. Посторонние логи в stdout не выводятся.

## 7. Входной контракт route_tasks

Обязательные поля верхнего уровня:

- `objective`: краткая цель, до 4 000 символов.
- `profiles`: от 1 до 16 профилей исполнителей.
- `tasks`: от 1 до 16 подзадач.

Необязательные настройки:

| Поле | Стандартное значение |
|---|---|
| `decision_model` | `nace-ai/drex-max` |
| `fallback_decision_model` | `typesafe/jev-1.14`, если основная модель Drex Max |
| `policy` | `balanced`; также доступны `economy`, `quality` |
| `max_parallel` | 3; допускается от 1 до 16, в пределах свободных слотов хоста |
| `min_probability` | 0.7 |
| `min_margin` | 0.15 |

`fallback_decision_model: null` отключает резерв. Если явно выбрана другая основная модель, резерв по умолчанию не добавляется. Поддержаны также `typesafe/jev-1.13`, `nace-ai/drex-v1.5`, `nace-ai/drex-v2.0` для явного сравнения.

Поля каждой задачи:

- `id` — уникальный идентификатор.
- `description` — конкретная работа, до 2 000 символов.
- `role` — текстовое название роли, до 120 символов.
- `acceptance` — критерии готовности, до 1 500 символов.
- `depends_on` — список предшествующих задач.
- `allowed_profiles` — непустой список допустимых профилей.
- `fallback_profile` — один из `allowed_profiles`.
- `context` — необязательный дополнительный контекст, до 3 000 символов.

Идентификаторы соответствуют `^[a-z][a-z0-9_]{0,47}$`. Неизвестные поля, дубликаты, неизвестные зависимости и циклы отклоняются. Размер входа и развёрнутого запроса ограничен 48 000 байтами. Полная схема находится в `schemas/route-input.json`.

Существующий список уровней `reasoning_effort`: `low`, `medium`, `high`, `xhigh`, `max`, `ultra`. Это ограничение текущего адаптера; оно не подтверждает поддержку каждого уровня каждой моделью или другим хостом.

Пример валидного входа. Имена моделей взяты из исходного Codex-примера; перед выполнением хост должен проверить их доступность:

```json
{
  "objective": "Найти причину ошибки поиска в каталоге и исправить её",
  "policy": "balanced",
  "max_parallel": 2,
  "profiles": [
    {
      "id": "reader",
      "model": "gpt-6-luna",
      "reasoning_effort": "high",
      "description": "Узкое чтение кода и поиск подтверждённых фактов",
      "cost_rank": 1
    },
    {
      "id": "engineer",
      "model": "gpt-6.1-sol",
      "reasoning_effort": "medium",
      "description": "Диагностика и реализация исправления с проверкой",
      "cost_rank": 2
    }
  ],
  "tasks": [
    {
      "id": "investigate",
      "role": "исследователь",
      "description": "Проследить обработку поискового запроса и найти место ошибки",
      "acceptance": "Подтверждённая причина с путями к файлам и способом воспроизведения",
      "depends_on": [],
      "allowed_profiles": ["reader", "engineer"],
      "fallback_profile": "engineer"
    },
    {
      "id": "fix",
      "role": "разработчик",
      "description": "Исправить подтверждённую причину и проверить результат",
      "acceptance": "Ошибка не воспроизводится, подходящие проверки проходят",
      "depends_on": ["investigate"],
      "allowed_profiles": ["engineer"],
      "fallback_profile": "engineer"
    }
  ]
}
```

Для `investigate` модель выбирает профиль. Для `fix` профиль закреплён основным агентом: один допустимый вариант не требует решения API. Если все задачи закреплены таким образом, внешнего вызова не будет.

## 8. Что отправляется в OpenRouter

Сервер вызывает:

```text
POST https://openrouter.ai/api/alpha/decisions
Authorization: Bearer <ключ из настроек>
Content-Type: application/json
```

Запрос содержит `model`, `state` и `questions`.

- `state`: цель, политика и данные задач.
- `questions`: один вопрос типа `choice` на каждую задачу с несколькими допустимыми профилями.
- `criteria`: идентификаторы профилей и описания их моделей, уровней рассуждения, возможностей и относительной стоимости.

Модель выбирает профиль, а не пишет код или свободный текст архитектуры. Восстановление цели и выделение задач остаются работой основного агента.

В API уходит переданный контекст задач. Сервер не читает репозиторий самостоятельно; минимизацию и отбор сведений делает основной агент.

## 9. Проверка ответа и резервирование

Для каждого ответа проверяются тип `choice`, допустимость выбранного профиля, совпадение ключей вероятностей с разрешёнными вариантами, числовые значения от 0 до 1, сумма около 1 и соответствие выбранного варианта максимальной вероятности.

Решение считается неуверенным, если вероятность выбранного варианта ниже `min_probability` или отрыв от ближайшего другого варианта ниже `min_margin`. Это эвристика, которую нужно калибровать на реальных задачах и отдельно для моделей.

Дальнейшая цепочка:

1. Принятые решения Drex сохраняются.
2. Jev получает вопросы только по оставшимся спорным задачам. Общий `state` сохраняется, поэтому повторный запрос всё ещё содержит контекст всех задач.
3. Если Jev также не дал принятого решения, назначается заранее переданный `fallback_profile`.

При сетевой ошибке, недоступности или повреждённом ответе основной модели допускается одна резервная попытка. HTTP 401/402/403 останавливают цепочку без второго обращения: это ошибки ключа, оплаты или доступа аккаунта. Дополнительного цикла повторов нет.

Параметр сетевого таймаута — 12 секунд на HTTP-вызов. Возможны две попытки плюс локальная обработка; фактическая общая задержка зависит от сети и ответа провайдера. Не гарантируется незаметная задержка.

## 10. Выходной контракт

Основные поля ответа:

| Поле | Содержание |
|---|---|
| `status` | `planned` либо `fallback_plan`, если хотя бы одна задача ушла на заранее заданный профиль |
| `executed` | Всегда `false`: сервер возвращает план |
| `assignments` | Задача, роль, профиль, модель, reasoning_effort, зависимости, данные решения |
| `execution_waves` | Очереди запуска с учётом зависимостей и max_parallel |
| `requested_decision_model` | Основная запрошенная модель |
| `backup_decision_model` | Настроенный резерв |
| `reported_decision_model` | Имя из последней попытки; при смешанном плане смотреть каждое назначение |
| `backup_used` | Был ли второй вызов |
| `attempts` | Запрошенная и фактическая модель, task_ids, ошибка, usage, стоимость и время каждой попытки |
| `api_called` | Было ли внешнее обращение в этом вызове |
| `api_error` | Последняя ошибка API/настройки, если есть |
| `api_cost_usd_this_call` | Сумма известной стоимости попыток; null, если есть неизвестная стоимость |
| `original_api_usage` | Учёт первоначального получения плана |
| `cache_hit` | Взят ли план из кэша |
| `elapsed_ms` | Измеренное локальное время операции |

`decision.source` имеет значения `decision_model`, `fixed_by_caller`, `fallback`. Дополнительные поля объясняют выбранную решающую модель, предложенный профиль, вероятности, отрыв и причину резервирования.

Волны запуска предполагают успешное завершение предыдущих зависимостей. Основной агент должен дождаться результата, передать его зависимой задаче и обработать неудачу. Сам список волн не свидетельствует о выполнении работ.

## 11. Кэш и ограничения расходов

Успешные планы кэшируются в памяти процесса на 600 секунд, максимум 128 записей. Ключ вычисляется через SHA-256 по нормализованному запросу и настройкам. Изменение задач, контекста, профилей или модели создаёт другой ключ. Планы с заранее заданным аварийным профилем не кэшируются.

При попадании в кэш внешнего вызова нет и `api_cost_usd_this_call` равен 0. Данные исходных попыток остаются как история первоначального получения плана.

Допускается до 32 внешних попыток за жизнь процесса, включая неудачные. После перезапуска счётчик сбрасывается. Это ограничение числа вызовов, а не лимит в долларах. Сервер не получает остаток средств OpenRouter или лимита подписки Codex. Таймаут может быть оплачен провайдером; неизвестная стоимость обозначается null.

## 12. Ключ и локальный запуск

Приоритет загрузки ключа:

1. Переменная окружения `OPENROUTER_API_KEY`.
2. Файл `~/.config/codex-decision-router/credentials.json`.

`CODEX_DECISION_ROUTER_KEY_FILE` позволяет задать другой путь. Сервер перечитывает ключ при некэшированном распределении; перезапуск для добавления ключа не требуется.

Для настройки пользователь запускает в Терминале:

```bash
python3 scripts/setup_key.py
```

Ввод скрыт. Файл создаётся с правами 0600, отдельно от пакета и кэша. Значение ключа не следует читать в контекст агента, выводить или переносить в handoff. Файлы `.env` и каталог `secrets/` не нужны для использования этого инструмента.

Сервер требует Python 3.10+ и использует стандартную библиотеку. Сторонние Python-зависимости отсутствуют.

```bash
# Запуск MCP-сервера
python3 server/main.py serve

# Безопасная проверка состояния
python3 server/main.py status

# Проверка запроса без API
python3 server/main.py preview \
  < <router-dir>/examples/architecture-code-research.json
```

CLI-команда `route` вместо `preview` делает платный вызов при наличии выбора и ключа. Коды возврата: 0 — план без аварийных профилей, 2 — fallback_plan, 1 — ошибка входа.

## 14. Подтверждённые проверки и ограничения

Ранее зафиксированы 29 успешных тестов логики: модели, зависимости и циклы, допустимые профили, вероятности, резерв, частичный переход на Jev, стоимость, кэш, лимит вызовов, ключи и MCP stdio через subprocess. HTTP-транспорт этих тестов подставной.

Codex app-server распознавал плагин, навык и все три MCP-инструмента. Версия 0.2.1 изменила инструкции запуска одним упоминанием; совпадение исходников и установленной копии проверено. При проверке 8 ноября реальный MCP router_status отвечает, плагин включён, ключ настроен.

Не установлены этой проверкой: качество распределения реальных задач, фактическая экономия лимита, задержка API на задачах пользователя, сквозной живой путь OpenRouter → назначение → реальный субагент, совместимость с Claude Code.

Структурная корректность ответа и высокая вероятность выбора не гарантируют качественного выполнения. Основной агент должен проверять результаты по критериям готовности и при необходимости менять назначение с учётом фактической ошибки.

## 15. Что учитывать в Claude Code

Универсальная часть — Python MCP-сервер с контрактом «задачи + профили → план». Он принимает строковые имена моделей исполнителей. Основные изменения для другого хоста потребуются в упаковке, инструкциях запуска и применении плана.

По документации Claude Code на дату подготовки, манифест плагина располагается в `.claude-plugin/plugin.json`, определения MCP могут находиться в `.mcp.json`, инструкции — в `skills/`. Для путей используется `${CLAUDE_PLUGIN_ROOT}`. Существующие Codex-файлы нельзя считать уже готовой упаковкой Claude. [Официальная схема плагина](https://code.claude.com/docs/en/plugins-reference).

Claude Code позволяет задавать модель субагента и поддерживаемый уровень effort; возможности зависят от модели и установленной версии. Адаптер должен использовать фактически доступные значения и учитывать переопределения окружения/политик. Имена Codex-моделей и параметр `reasoning_effort` не следует механически переносить в вызовы Claude. [Официальная документация субагентов](https://code.claude.com/docs/en/sub-agents).

Возможные цели адаптации нужно различать:

- **Claude управляет своими субагентами.** Составляются профили моделей Claude, а план применяется штатными средствами Claude Code. Рабочая тарификация определяется способом его запуска; OpenRouter остаётся только для Drex/Jev.
- **Claude управляет субагентами Codex.** Нужен отдельный мост к Codex для запуска, разрешений, ожидания и получения результатов. В этом исходнике такого моста нет. Простое подключение MCP-маршрутизатора его не создаёт.
- **Claude только изучает или дорабатывает исходник.** Он может работать с текущей папкой проекта, не меняя механизм исполнения и установленную интеграцию Codex.

Для последующей адаптации следует сохранить выбранную цепочку Drex Max → Jev 1.14, проверки допустимых профилей, обработку неопределённости, минимальный контекст и отсутствие рабочих вызовов через OpenRouter. Изменения хоста нужно отделить от универсального маршрутизатора. Текущие поля `native_codex_plan`, сообщения про Codex, шаблоны профилей и инструкция навыка также требуют согласования с целевым хостом.

Нельзя описывать текущий инструмент как полноценный автономный исполнитель: выбор и применение плана разделены. Нельзя считать настроенный ключ подтверждением успешной оплаченной операции. Нельзя называть эвристический `cost_rank` измеренной экономией подписки. Публикация, доступ к секретам и другие внешние действия сохраняют обычные разрешения хоста.

## 16. Короткий контекст для следующего агента

Есть установленный и включённый Codex-плагин 0.2.1 в `<router-dir>`. Он маршрутизирует подзадачи между штатными субагентами Codex, используя Drex Max через OpenRouter и Jev 1.14 как резерв. MCP-сервер возвращает проверенный план; исполняет его основной агент по SKILL.md. Достаточно явного упоминания навыка. Ключ настроен отдельно, его содержимое не нужно читать. Универсальный контракт можно переиспользовать, а интеграцию Claude Code нужно проектировать и проверять отдельно. Перед изменениями прочитай исходники и уточни целевой хост исполнителей, если это не указано в следующем задании пользователя.
